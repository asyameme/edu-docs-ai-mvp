# Переход на версионный граф v0.8

12.11.2026. Локальная ветка feature/versioned-graph-storage от origin/main 2df744e.
Наша интеграция парсера/генератора уже включена в main через PR 29.

## Требуемый результат

Единственное постоянное представление состояния — состав графа и переиспользуемые
редакции. SnapshotV2 собирается при чтении. Сохраняются порядок массивов, значения,
источники, оригиналы, подтверждения, старые версии и закреплённые входы генерации.
История защищена БД. Новые версии записывают журнал правок. Temporal управляет
выполнением, таблица операций хранит запросы и предметные результаты.

Контракты документов, код парсера и генератора сохраняются. Новая миграция
переносит существующие данные в одной транзакции с проверкой обратной сборки;
старые миграции не переписываются. Рабочая база при разработке не обновляется.

## Реализация

1. Выполнено: fetch всех веток; проверено включение a2519fc в main; создана новая
   локальная ветка. Коммит и отправка на GitHub не требуются.
2. Реализовано: миграция 0006, сборка SnapshotV2 при чтении, переиспользование
   редакций, restore прежнего графа и атомарная запись журнала фактической разницы.
3. Реализовано: импорт/анализ/генерация сохраняют ссылки на состояния и артефакты;
   JSON документа хэшируется по JCS RFC 8785 в UTF-8. Размер и SHA-256 проверяются
   при чтении артефакта. Вход генерации закреплён за sealed-графом.
   Активный статус генерации читается из Temporal; флаг started_at в отчёт больше
   не записывается. Сохранённый результат доступен после удаления истории workflow.
4. Проверено в отдельных БД: перенос V1/V2 и подтверждений, ZIP и оригиналы,
   конкурентное сохранение, неизменяемость, обычная роль, реальные документы,
   HTTP/Temporal/Worker и контрольный HTTP-анализатор. Полноценный ML-анализатор
   этим не проверялся; задача касается сохранения и обмена данными.

Критерии приёмки: точная обратная сборка истории и хэшей; одна правка переиспользует
неизменённые редакции; restore сохраняет историю; неправильные ссылки и изменения
sealed отклоняются; повтор импорта не меняет вход уже принятой генерации; JSON
разбора хранится в артефакте, а не копируется в metadata/report/parameters.

## Уточнения реализации относительно проекта v0.8

Таблиц по-прежнему 19. `graph_source_links.public_id` сохраняет внешний ID
свидетельства, а source_link_id указывает на внутреннюю неизменяемую запись.
Это позволяет восстановить старые результаты разных попыток, где один внешний
ID использовался с разными наблюдениями, включая различие 0 и false.

У восстановленного исторического результата producing_attempt может быть NULL:
старый код не всегда сохранял номер попытки в закреплённом входе генерации.
Известная задача сохраняется, неизвестный номер не подменяется догадкой. Новые
импорты сохраняют точный номер попытки. ID, порядок, значения и хэши версий
проверяются до удаления прежних таблиц; при несовпадении миграция откатывается.
Внешние FK или представления над старой схемой требуют отдельного переноса.

Прежние версии V1 остаются V1 в хранилище. При выдаче через API используется
действующий DTO V2 с заполненными значениями по умолчанию; история не переписывается.

Исходный ответ анализа до преобразования его ID сохраняется отдельным неизменяемым
файлом аудита, с размером и JCS SHA-256. Он не является рабочей версией программы.
Конфликтные старые ответы без опубликованной версии тоже сохраняются в аудит,
а не превращаются в фиктивную принятую версию. Для обновления нужен доступ мигратора
к тому `artifact-files`; транзакция БД может оставить неиспользуемый файл аудита
после отката, но не частично перенесённые таблицы.

При сохранении версии, восстановлении, выборе решения или подтверждении API принимает
имя подписи и записывает его в соответствующее действие и журнал созданной версии.
Интерфейс review запрашивает имя один раз и сохраняет его в браузере.
Это подпись, введённая самим пользователем; она не подтверждает личность, потому
что авторизации пока нет.
Старой истории не приписываются придуманные авторы или время отдельных правок.

Хэш `parser_config_hash` проверяется по правилу контракта review — компактному JSON
с сортировкой ключей. Для JSON-артефактов парсера `sha256` считается по каноническим
JCS-байтам UTF-8; эти два правила относятся к разным полям и не взаимозаменяемы.

## Развёртывание

Рабочую БД этим заданием не обновляли. Перед применением 0006 остановить старые API
и воркеры и сохранить проверенную резервную копию PostgreSQL вместе с artifact-files.
Миграция рассчитана на текущую цепочку до 0005; она не исправляет сторонние схемы
или повреждённые исторические данные. Откат выполняется восстановлением копии.

Миграции выполняет владелец таблиц. Для эксплуатации API/Worker нужен отдельный
логин PostgreSQL, без владения таблицами и SUPERUSER. Набор прав для уже созданного
логина задаёт backend/scripts/grant_graph_runtime.sql; также нельзя предоставлять
ему право CREATE в схеме public или права администратора. В локальном Compose
сохранён прежний способ настройки подключения: реальные учётные записи и пароли
этой работой не менялись. Запрет изменения истории триггерами проверен отдельно
от проверки того, что обычная роль не может отключить эти триггеры.

## Воспроизводимые проверки

Запускать только с отдельными БД и тестовыми сервисами:

- `GRAPH_TEST_DSN` — PostgreSQL с применёнными миграциями: tests/test_graph_storage.py.
- `GRAPH_MIGRATION_TEST_DSN` — отдельная пустая БД (SQLAlchemy psycopg URL):
  tests/test_graph_migration.py; тестовые DDL и данные откатываются.
- `RUN_INTEGRATION=1`, `GENERATION_WORKER_TESTS=1`, `GENERATION_REAL_DOC_TESTS=1` —
  настоящий локальный парсер, Temporal/Worker/API и tests/originals.
- `PARSER_FIXTURE_TESTS=1`, `REVIEW_FIXTURE_TESTS=1` — отдельный режим с контрольными
  HTTP-серверами из backend/tests. Для test_stage2_api лимит загрузки 50 МиБ.

Нельзя одновременно запускать тесты режима недоступного/локального парсера и
режима контрольного HTTP-парсера против одного воркера. Параметры PostgreSQL и
Temporal тестового процесса должны указывать на тот же изолированный стек.
