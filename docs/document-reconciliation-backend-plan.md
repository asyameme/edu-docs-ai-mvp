## Цель и границы

Реализовать поток:

`импорт → отдельные JSON → согласование → выбор всех обязательных решений → граф → check → подтверждение → генерация`.

Чтение через чат доступно после готовности графа; отдельного требования подтверждать
версию перед чтением промпт не добавляет. Принятая правка чата создаёт новую версию,
для генерации которой нужны новая проверка и подтверждение.

Сохранить оригинальные байты, версии, наблюдения источников и существующую архитектуру
Temporal/версионного графа. Пользовательские решения принимаются отдельными запросами;
Worker не ждёт человека внутри бесконечного Workflow.

В этот план входят девять пунктов промпта. Не входят новые предметные алгоритмы
валидации, автоматическое назначение правильного документа, векторный поиск и
самостоятельная переработка UI или общих контрактов команды.

Текст файла использован как требования к плану. Реализация начата после отдельного
явного поручения пользователя; frontend и общие контракты не редактировались.

## Порядок исполнения

### 1. Зафиксировать протокол и модель состояния

Работа: `review_contract.py`, примеры review, `domain.py`, review API/repository/storage.

- Взять существующие PrepareRequestV2/AnalysisV2 и `/analyze`, CheckRequest/CheckResult
  и `/check` как исходную границу. Не менять общие модели парсера.
- Развести состояния предметного результата: документы готовы; ожидается выбор;
  граф построен; проверка завершена; версия подтверждена. Текущее выполнение брать
  из Temporal, предметный итог хранить долговечно.
- Развести V1 и V2 по сохранённой версии протокола задачи. Старые отчёты и уже
  принятые V1-задачи должны оставаться читаемыми; обновление Worker не переключает
  протокол задания. Исторические графы не удалять.
- До графа хранить закреплённый манифест, ссылки на исходные parsed-артефакты,
  AnalysisV2, выбранные варианты и ревизию согласования. Каждое решение неизменяемо,
  содержит подпись и родительскую ревизию.
- Проверить представление такой ревизии в существующих API версий: frontend уже
  ожидает version_id и review-детали для показа выбора. `graph_ready=false` сам по
  себе не заменяет хранение предграфового состояния. Нельзя показывать прежний граф
  как результат нового анализа или создавать нормализованные узлы ради получения ID.
- Отдельно оформить решение хранения до реализации: текущий insert_version сохраняет
  граф, а pack_tree требует существующего parsed-артефакта с соответствующим хэшем.
  Нужны ревизии согласования без нормализованного графа и отдельные артефакты выбранных
  JSON. Если существующие связи этого не позволяют, подготовить минимальную новую
  миграцию с проверкой старой истории; заранее обещать отсутствие миграций нельзя.

Приёмка: до принятия всех решений нет построенного графа; API может вернуть
документы, находки и варианты, а повторное открытие продолжает ту же ревизию.
Несовместимость с текущим UI/контрактом оформить конкретным предложением на согласование.

### 2. Завершать импорт без нормализации — пункт 1

Работа: `import_activities.py`, `import_repository.py`, `import_api.py`, `graph_storage.py`.

- Оставить отдельный неизменяемый parsed-артефакт каждого документа и закреплённый
  результат попытки. Сохранить member_name, sha256, document_id, ошибки файлов и parse_issues.
- Убрать to_snapshot/save_graph из нового пути завершения импорта. Перенести сбор
  диагностик парсера из графового адаптера в самостоятельную обработку результата.
- Сохранить completed/partial/failed, retry отдельных файлов и защиту от устаревшей
  попытки. Подготовка, уже принятая в работу, использует свой закреплённый манифест.

Приёмка: одинаковые имена не объединяют документы; `/imports/{id}/result` соответствует
текущему ImportResultRead; импорт не создаёт нормализованных сущностей/связей.

### 3. Перевести подготовку на документный анализ — пункт 2

Работа: `review_activities.py`, `review_repository.py`, `review_logic.py`, HTTP fixtures.

- Для новых заданий формировать PrepareRequestV2 без base_snapshot и принимать
  AnalysisV2 без candidate. Проверить принадлежность документов, вариантов и artifacts
  закреплённому пакету; каждый вариант проверить на применимость отдельно.
- Сохранять исходный ответ и нормализованный отчёт, ruleset/config/revision, источники
  документов и стабильные ID находок. Повторы используют тот же job_id.
- Различать завершение анализа и готовность графа. Если есть requires_decision,
  опубликовать состояние ожидания выбора; иначе перейти к сборке графа.
- Не разрешать позднему результату анализа перезаписать новую текущую версию.

Приёмка: V2-примеры проходят настоящий Activity-путь; candidate в V2 отклоняется;
повтор Activity не создаёт второй отчёт или вторую ревизию.

### 4. Применять выбор к документам — пункты 3–4

Работа: отдельные чистые функции документных изменений, ReviewRepository.decide.

- Поддержать set_document_value с document_id и строгим JSON Pointer: экранирование
  ~0/~1, существующие ключи и индексы, запрет append/создания отсутствующего поля.
- Различать отсутствие поля и null; expected_old_value проверять с явной политикой
  JSON-типов, не считать true равным 1. Выбор накладывать воспроизводимо на исходный
  пакет с полным набором действующих решений, не на случайную промежуточную копию.
- Защитить meta, source_ref и parse_issues, включая замену родительского объекта,
  которая могла бы косвенно изменить защищённые вложенные данные.
- Проверять конфликт одинакового пути и пересекающихся путей родитель/потомок.
  Вариант атомарен; конфликтующие выборы отклоняются целиком. Не распространять
  изменение автоматически на одноимённые записи других документов.
- Повтор ключа запроса возвращает прежний результат. Конкурентные выборы проверяют
  ожидаемую ревизию; проигравший запрос получает конфликт, не затирает чужое решение.
- Пока остался requires_decision без выбранного варианта, сборку не запускать.
  Само наличие blocking-находки без вариантов не придумывает пользовательское решение:
  оно должно препятствовать подтверждению согласно профилю проверки.

Приёмка: последний обязательный выбор запускает одну сборку; смена выбора создаёт
новую ревизию, аннулирует применимость прежней проверки и подтверждения.

### 5. Строить граф с исходным происхождением — пункты 4–5

Работа: `document_adapter.py`, review storage, вход генерации.

- Строить сущности и связи по выбранным JSON только после завершения согласования.
  Нужна служебная привязка записи к document_id + пути исходной записи, независимая
  от изменяемого кода/названия; одноимённые документы и одинаковые координаты различать.
- Attributes отражают выбранный итог, SourceRef сохраняет координаты оригинала,
  SourceLink.observed_value — исходное значение из первоначального parsed-артефакта.
  Построение по исправленному JSON с последующей записью его значений как observed
  недопустимо. Для изменённых ключей отдельно проверить разрешение связей; не
  исправлять другие поля без явно выбранной документной операции.
- При неоднозначном соответствии не назначать первый источник и не выдумывать
  координаты. Вернуть явный отказ полной сборки/проверки с сохранёнными решениями.
- Публиковать готовую версию атомарно, graph_ready=true только после успешной сборки.

Приёмка: выбор 144 вместо108 даёт attributes=144, observed_value=108; оригинальный DOCX
и parsed неизменны; граф и источники восстанавливаются из хранения без потерь.

### 6. Подключить стадии проверки и запреты — пункты 6–8

Работа: review/check, chat repository/activities, generation repository/activities,
`worker/agent/validation_adapter.py` и адаптер локального исполнителя.

- Согласовать с командой анализатора распределение правил между документным `/analyze`
  и графовым `/check`, обязательность, статусы и coverage. Наличие готового обработчика
  не даёт Backend права самостоятельно менять смысл или обязательность правила.
- Для стадий закреплять полный безопасный профиль и ревизию исполнителя, не хранить
  ключи. До выполнения графовой проверки проверять graph_ready и точную version_id/hash.
- Сохранить технические наработки 2d2af47: document_id в evidence, бюджет LLM,
  совместимость исполнителя, устойчивые ID, needs_review. Перенос в новой ветке от
  обновлённой main делать с разбором конфликтов; старый prepare, сразу создающий
  candidate, не переносить в V2-путь. Фронтенд из старого коммита автоматически не вливать.
- В validation_adapter записывать rule_code=result.rule_id, type=finding.code,
  rule_revision из результата/эффективного профиля; если revision отсутствует,
  допустим воспроизводимый отпечаток точной конфигурации правила, но не константа1.
  Политику severity подтвердить, не понижать все нарушения до warning самостоятельно.
- needs_review и неполное обязательное покрытие не превращать в passed. Текущий
  общий coverage-контракт main не разрешает needs_review: его совместимость с локальным
  исполнителем — конкретный вопрос согласования, без молчаливого расширения схемы.
- На сервере блокировать check до графа; confirm до графа, завершённого актуального
  check и разрешения blocking; чат/агента до графа. Проверять также отправку хода и
  выполнение уже поставленного задания, не только создание чат-сессии.
- Генерация требует проверенную подтверждённую версию и закрепляет именно её вход.
  Проверять ограничения повторно в Worker; запросы API в обход UI не должны их обходить.

Приёмка: прямые запрещённые запросы отклоняются; проверка старой версии не подтверждает
новую; draft не активируются автоматически; `/analyze` и `/check` сохраняют согласованный обмен.

### 7. Генерировать накопленный итог правок чата — пункт 9

Работа: `generation_bridge.py`, Backend-реализация ChatWritePort в необходимом объёме,
`proposal_apply.py` и сбор входа `build_generation_documents`.

- Использовать выбранную итоговую версию графа и её полную историю происхождения,
  а не только список changes последнего ChangeProposal. Выборы согласования тоже
  должны попасть в последующий документный патч.
- Сравнивать итоговые значения с исходными DOCX/observed_value. Две правки разных
  полей сохраняются обе; 108→144→180 даёт итог180; возврат к108 не оставляет патч144.
- Сохранять старые версии и исходные наблюдения; новую версию после правки отдельно
  проверять и подтверждать. Запрос генерации закреплять за версией, не за current
  на момент выполнения. Посторонние изменения и другие сессии не подмешивать.
- Изменения без достоверного отображения в DOCX отклонять явно. Не добавлять
  структурное редактирование, если его нет в согласованном контракте.

Приёмка: два последовательных сообщения с принятыми правками → итоговый DOCX содержит
обе правки и открывается; оригинал не изменён; повтор генерации использует тот же вход.

### 8. Приёмка и выпуск

- Сначала регрессии на требования, затем реализация по шагам. Проверки JSON Pointer,
  null/отсутствия, protected-полей, конфликтов и provenance — чистые тесты.
- Интеграционные проверки в отдельной PostgreSQL/Temporal: импорт без графа;
  AnalysisV2 с конфликтами и без них; все варианты/последний выбор; retry, гонки,
  рестарт Worker, устаревший результат, чтение старых V1-отчётов.
- Сквозной набор: реальный ZIP → отдельные parsed → согласование → выбор → граф →
  check → confirm → доступ чата → последовательные правки → check/confirm → DOCX/ZIP.
  HTTP-фикстура доказывает контракт, настоящий анализатор и LLM проверяются отдельно.
- Проверить существующий UI без его изменения. Если он не может отобразить состояние
  до графа, оформить минимальный конкретный запрос на согласование UI/контракта.
- Выполнить относящиеся к изменениям Backend/agent/validation/generation tests,
  Ruff, схемы, Docker build; миграцию, если нужна, прогнать на копии старых данных.
- Обновить документацию API, модель состояния, команду запуска и отчёт проверок.
  Отдельно перечислить проверки, которые не удалось выполнить из-за модели/сервисов.

## Зависимости, которые нельзя подменить предположением

Обновление 2026-11-17: существующая разметка фаз найдена в `origin/feature/validator`
(`aee3532`, вершина `287adcc`). Она неполна и относится к другому набору правил;
проверка конфигурации из этой ветки отклоняет R-08-semantic без phases.
Техническая схема стадий реализована для текущего профиля из 17 правил по этому
источнику и по просьбе пользователя; сопоставление и остаточные вопросы к команде:
[stage7-rule-agreement.md](stage7-rule-agreement.md).

1. Команда анализатора подтверждает стадии правил и семантику coverage/severity/revision.
2. Представление предграфовой версии проверено на существующем UI и схеме хранения;
   необходимые изменения общего контракта/UI согласованы конкретным diff.
3. Определена совместимость needs_review с опубликованным V2, без смены смысла статуса.
4. Для живой приёмки доступны анализатор и модель; отсутствие доступа не выдаётся за
   доказательство работающего внешнего сервиса.

Эти зависимости не мешают начать Backend-реализацию хранилища результатов,
чистых документных изменений и регрессионных тестов. Продуктовые политики не
выбирать автоматически ради прохождения тестов.

## Предлагаемое разбиение работы

1. Импорт документов, предграфовое состояние и совместимость исторических данных.
2. Prepare V2, документные решения, сборка графа с исходным provenance.
3. Стадии check, адаптер находок, ограничения chat/confirm/generation и перенос валидатора.
4. Накопительная генерация после правок чата и полная приёмка.

Каждая часть завершается соответствующими проверками; весь план считается выполненным
только после прохождения согласованного сквозного сценария и фиксации результатов.
