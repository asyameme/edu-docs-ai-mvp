## Разбор блока парсера

## Цель

Определить тип документа, найти нужные разделы и перенести данные в JSON по Pydantic-схеме. Каждая сущность получает `source_ref`, проблемы разбора записываются в `parse_issues`.

Алгоритм описывает РПД и РПП. Результат - один JSON на файл. Образцы структуры:

- [rpd_.json](../backend/worker/parser/json_examples/rpd_.json) - данные РПД.
- [curriculum_.json](../backend/worker/parser/json_examples/curriculum_.json) - дополнительный пример для УП.
- [models.py](../backend/worker/parser/models.py) - поля и ограничения моделей.

Инструменты: Python, `python-docx`, `openpyxl`, Pydantic, `json`.

## 1 Классификация

1. Прочитать титульный блок Word, включая таблицы.
2. Для поиска привести текст к одному регистру, убрать лишние пробелы и переносы. Учесть разрядку букв: «Р А Б О Ч А Я П Р О Г Р А М М А».
3. Определить тип по титулу:

| Текст на титуле | `meta.doc_type` |
| --- | --- |
| «Рабочая программа» и «учебной дисциплины» | `RPD` |
| «Рабочая программа» и «практики» | `RPP` |

4. Выбрать список разделов для этого типа и отметить обязательные разделы шаблона.
5. Если тип определить нельзя, записать причину и остановить разбор файла.

Название файла использовать только как подсказку.

## 2 Поиск разделов

### РПД

| Номер | Заголовок или его признаки | Данные |
| --- | --- | --- |
| 1.2 | Требования к подготовленности; пререквизиты | Предшествующие дисциплины |
| 1.3 | Перечень результатов обучения; learning outcomes | Компетенции, индикаторы, результаты обучения |
| 2.1 и подразделы | Организация учебных занятий; основной курс | Семестры, ЗЕТ, часы, формы контроля |
| 2.2 | Структура и содержание учебных занятий | Темы, виды занятий, часы |
| 3.1.3, если есть в шаблоне | Методика контроля и аттестации; критерии оценивания | Шкалы и критерии оценки |
| 3.1.4 | Методические материалы контроля; оценочные средства | Оценочные средства и связи с индикаторами |

### РПП

| Номер | Заголовок или его признаки | Данные |
| --- | --- | --- |
| 1.5 | Требования подготовленности к прохождению практики | Предшествующие дисциплины, если названы |
| 1.7 и подраздел 1.7.2, если есть | Перечень профессиональных компетенций | Компетенции, индикаторы, результаты обучения |
| 2.1 | Организация практики | Семестры, ЗЕТ, часы, если указаны |
| 2.2 | Структура и содержание практики | Этапы и содержание |
| 3.1.1 | Виды и формы контроля и аттестации | Формы контроля |
| 3.1.3.1 | Методика контроля и аттестации | Процедуры контроля |
| 3.1.3.2 | Методика и критерии оценивания | Шкалы и критерии оценки |
| 3.1.3.3 | Оценочные средства; контрольно-измерительные материалы | Средства оценки, задания, связи с индикаторами |

Номера могут отличаться. В РПП таблица результатов встречается как в 1.7.2, так и внутри 1.7 без отдельного подзаголовка. Отсутствие необязательного раздела, например 3.1.3 РПД, не считается ошибкой.

### Как искать

1. Читать абзацы и таблицы в порядке документа.
2. В заголовке отделить номер от текста. Сравнивать текст без учета регистра, лишних пробелов и переносов.
3. Проверять известные варианты: например, «Требования к подготовленности» и «Требования подготовленности», с английским пояснением и без него.
4. Использовать номер как дополнительный признак. В ссылке на источник сохранять фактический номер.
5. Исключать оглавление, ссылки «см. раздел...» и пункты заданий.
6. Считать концом раздела следующий заголовок того же или более высокого уровня. Вложенные подразделы входят в раздел.
7. Искать таблицы по названиям колонок. Обрабатывать все подходящие таблицы, учитывать многострочные шапки и объединенные ячейки.

Если обязательный раздел не найден - `not_found`. Если раздел найден, но пуст или не разбирается, записать отдельную проблему с его координатами.

## 3 Перенос в JSON

### Соответствие схеме

| Данные | Поле JSON |
| --- | --- |
| Название дисциплины, семестры, ЗЕТ, часы, контроль, пререквизиты | `disciplines` |
| Код и формулировка компетенции | `competencies` |
| Код и текст индикатора, родительская компетенция | `indicators` |
| Результаты «знать», «уметь», «владеть» | `learning_outcomes` |
| Оценочные средства | `assessment_tools` |
| Тема, вид занятия, часы | `course_content` |
| Оценка СПбГУ, ECTS, баллы, критерии | `score_scale` |
| Связи между сущностями | `relations` |
| Строки УП в дополнительном примере | `curriculum_items` |

Для практики предполагается использовать `disciplines` при `meta.doc_type="RPP"`: отдельной модели практики нет. В таблице сущностей команды `CreditUnits/Hours` соответствует полям часов и ЗЕТ, `CourseContent` - `course_content`, `EducationalProgram` - `program`.

### Порядок переноса

1. Сопоставить колонки с полями модели. Пропустить шапки. Итоги часов и ЗЕТ сохранить отдельно от видов работы.
2. Разделить несколько индикаторов или результатов с собственными кодами на отдельные объекты.
3. Сохранить коды, описания и порядок записей. Допустимо убрать лишние пробелы и привести «знает / умеет / владеет» к `знать / уметь / владеть`. Не исправлять коды по догадке. Неизвестный код сохранить для дальнейшей проверки каталога.
4. Результатам обучения назначить уникальные в файле `local_id`: `LO-001`, `LO-002`. Сохранить собственный код результата, если он есть.
5. Добавить `source_ref` каждой сущности и связи.
6. Создать связи, подтвержденные таблицей или текстом: дисциплина формирует компетенцию, компетенция имеет индикатор или включает результат, индикатор проверяется оценочным средством. Родителя определять по структуре и коду. Проверить существование объектов локальных связей.
7. Проверить объекты через Pydantic. Если обязательных данных нет, пропустить неполный объект и зависимые связи, добавить `parse_issue` и продолжить разбор.
8. Собрать `ParserOutput`. В `meta` указать тип, имя файла, SHA-256 и `parser_config` - версию правил разбора.
9. Выполнить `ParserOutput.model_validate`, сохранить JSON и прочитать через `ParserOutput.model_validate_json`. Проверить, что значения и связи не потерялись и не продублировались.

### Что важно сохранить

- Часы и ЗЕТ переносить без округления. Различать значения титула, таблицы, семестров и общего итога. Расхождения не исправлять при разборе.
- Не складывать основные часы с подытогами и пересекающимися показателями «активных форм». ЗЕТ не записывать в `hours_by_kind`.
- Не вычислять отсутствующие часы по формуле `ЗЕТ × 36`: это правило последующей сверки сопоставимых показателей. Если РПП отсылает к УП, зафиксировать отсутствие локальных данных.
- Сохранить реальные повторы и их координаты для проверки дублей. Повтор одной объединенной ячейки не создает новую запись. Упоминания одной компетенции в разных документах допустимы.
- Если у текстовой темы нет часов, не подставлять ноль ради создания `CourseTopic`.

В схеме пока нет отдельных полей для регистрационного кода дисциплины, языка обучения, полного распределения часов и ЗЕТ по семестрам и нескольких противоречащих значений. Также нужно согласовать прямую связь результата с индикатором. Такие данные сохранять с координатами во внутреннем результате разбора и отмечать `manual_review`. Его формат нужно согласовать; новые поля в JSON самовольно не добавлять. Дробные значения, не подходящие текущим целочисленным полям, не округлять.

### source_ref

- `file` - имя исходного файла.
- `section` - фактический раздел.
- `table` - номер таблицы тела Word с 1.
- `row` - исходный номер строки с 1, включая шапку. Для Excel - номер строки листа.
- `col` - номер столбца с 1, если нужна конкретная ячейка.

Строки после фильтрации не перенумеровывать. Для абзаца указывать файл и раздел, без `row`. Если данные взяты из нескольких мест, в `source_ref` указать основное, остальные координаты сохранить во внутреннем результате разбора. Дополнительные разделы можно перечислить в `section`, например `1.2;2.1`.

Имя файла связывается с сохраненным исходником через `meta.file_hash`. Хеш различает содержимое файлов; версию программы определяет модуль хранения.

```json
{
  "source_ref": {
    "file": "РПД_матанализ1.docx",
    "section": "1.3",
    "table": 1,
    "row": 2
  },
  "code": "УК-1",
  "formulation": "способен осуществлять поиск, критический анализ и синтез информации, применять системный подход для решения поставленных задач"
}
```

### parse_issues

Одна запись описывает одну проблему разбора.

| Категория | Причина |
| --- | --- |
| `not_found` | Не найден обязательный раздел или таблица |
| `empty_cell` | Пустая обязательная ячейка |
| `unparsed_row` | Строка не разобрана |
| `unexpected_format` | Неподдерживаемый формат или значение |
| `ambiguous` | Несколько неразрешимых вариантов |
| `manual_review` | Нужна ручная проверка |

```json
{
  "category": "not_found",
  "message": "Не найден раздел с перечнем результатов обучения",
  "severity": "warning",
  "source_ref": {"file": "example.docx"}
}
```

Если раздел не найден, строку не указывать. После записи проблемы продолжать остальные разделы. Если вместо таблицы дан текст, сначала проверить допустимый вариант разбора; при неудаче добавить `manual_review` или `unexpected_format`.

Расхождение успешно прочитанных часов с УП, неизвестный каталогу код и различие описаний относятся к следующему этапу проверки по правилам проекта. Они не исправляются парсером. Pydantic проверяет структуру и ограничения моделей, но не достоверность данных. Предварительная серьезность нарушения из реестра правил не задает автоматически `severity` проблемы разбора.

## Проверка результата

- Тип определен по титулу, разделы найдены по заголовкам с учетом шаблона.
- Коды, тексты, числа, повторы и ссылки сохранены.
- Неполные объекты пропущены с объяснением в `parse_issues`.
- JSON проходит Pydantic и повторное чтение без потерь.

Примеры РПД и УП задают структуру. Значения и координаты нужно брать из исходника: в примере УП есть ошибки часов и строк. Сверка документов, проверка норм и управление версиями выполняются после разбора.

## Модули реализации

- `common.py` - текст, числа, заголовки и границы разделов.
- `results.py` - компетенции, индикаторы, результаты обучения и связи.
- `discipline.py` - название, нагрузка, формы контроля и пререквизиты.
- `content.py` - таблицы содержания. Диапазоны часов не заменяются одним числом.
- `assessment.py` - оценочные средства, явные связи с индикаторами и шкалы.
- `parse_rpd.py` и `parse_rpp.py` - сборка результата и запуск соответствующего парсера.

Проверки извлечения запускаются из корня проекта:

```bash
python -m unittest discover -s tests -p 'test_parse_rp*.py' -v
```

## Передача результата валидатору

Контракт версии 1 сохраняется. У практики общий объем передается в `disciplines`, а посеместровые значения доступны из `extract_practice_workload` и перечисляются с источниками в `manual_review`. Эти сообщения не заменяют структурированных полей для автоматической сверки по семестрам. Общие 18 ЗЕТ нельзя сравнивать с 3 ЗЕТ отдельного семестра.

Для автоматической сверки языка обучения, ЗЕТ титула и нагрузки по семестрам нужны согласованные поля контракта и правила валидатора. `parse_issues` должны учитываться при определении полноты проверки: отсутствие находок валидатора при пропущенных правилах не подтверждает корректность документа.

Если практика отсылает за нагрузкой к УП, отсутствующие часы не вычисляются из ЗЕТ. До получения нагрузки объект `Discipline` может отсутствовать. Прочитанные темы тогда не добавляются как записи без родительской дисциплины; их значения и координаты фиксируются в `manual_review`. Оценочные средства и шкалы, имеющие собственные источники, сохраняются.

Конфигурация проверки суммы часов должна учитывать все сопоставимые виды работы, включая семинары и лабораторные занятия. Извлеченные ключи и значения не исправляются ради неполного списка компонентов в валидаторе. Подключение к Temporal, хранению, интерфейсу проверки и LLM-fallback выполняется в последующих слоях.
