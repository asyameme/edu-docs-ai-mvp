# Контракт анализа и подтверждения — предложение Backend / ML v1

Эти примеры искусственные. Они показывают обмен и не доказывают извлечение данных
из реальных документов. Входные документы используют только общие контракты парсера V2.

- prepare-request.json → POST ANALYSIS_URL/analyze → analysis-response.json.
- check-request.json → POST ANALYSIS_URL/check → check-response.json.
- contract.schema.json — JSON Schema 2020-12 четырёх сообщений.
- app/review_contract.py — исполняемые Pydantic-модели, источник схемы.

Версия обмена schema_version=1 отличается от версии снимка: новый снимок использует
schema_version=2. Снимки V1 больше не принимаются приложением. Общие модели документов команды используются без изменений.

## Вход анализа

Передаются ID задачи/программы/входной версии, базовый снимок и точный манифест файлов:
document_id, sha256 и сохранённый документ V2 каждого оригинала. При наличии
original_url анализатор может получить исходные байты, если промежуточный парсер
не извлёк нужные поля. Адрес строит Backend; ML не передаёт Backend произвольные
пути или URL для скачивания. В Compose базовый адрес — http://api:8000; внешний
ML-сервис должен иметь доступ к ANALYSIS_ORIGINAL_BASE_URL.

Idempotency-Key равен job_id. При повторе нельзя создавать другое содержимое той же
операции. Документы, хэши и входная версия зафиксированы при создании запроса,
дальнейший retry импорта их не заменяет.

## Выход анализа

candidate — неподтверждённый SnapshotV2. ML сопоставляет общие сущности между файлами
и возвращает их канонический состав; одинаковое название само по себе недостаточно.
Новые UUID Backend отображает в пространство конкретной подготовки; UUID сущностей
из базового снимка сохраняются. Все ID ответа должны быть однозначны между видами
объектов. Документы обязаны совпадать с манифестом. Нельзя присылать review/confirmation.

Источник содержит UUID документа и реальное место в оригинале — locator. Указывайте
раздел/таблицу/ячейку, лист XLSX или страницу PDF, когда они действительно известны.
Не подставляйте фиктивную страницу1. source_links связывает конкретное поле сущности
или связи с источником и исходным observed_value. Неизвестное значение — value:null.
Разные значения одного поля сохраняются раздельно, исходные наблюдения не затираются.
Коды передавайте строками с исходными нулями; точные дробные значения предпочтительно
строками с единицей, а не округлённым float. matrix_value — целое0 или1, отсутствие
связи не означает установленный ноль. confidence при наличии — число0..1.

issues содержит rule_code/revision, тип, severity=warning/blocking, сообщение,
source_ref_ids и requires_decision. Для выбора нужны variants с уникальными UUID,
подписями и типизированными изменениями. Часы и ЗЕТ — разные поля; варианты обязаны
описывать конкретные изменения, а не сравнивать разные единицы как одно значение.
Поддержаны set_attribute, add/remove_entity, add/update/remove_relation. Изменения
адресуются UUID; установка поля разрешена только внутри attributes. Удаление сущности
требует согласованного удаления зависимых связей. Свободный JSON Patch не исполняется.

ruleset хранит ID/revision, полную безопасную конфигурацию, обязательные правила и
типы документов. В config не должно быть токенов, паролей или заголовков авторизации.
coverage сообщает итог каждого запрошенного правила. Для failed требуется issue;
issue с прошедшим правилом недопустим. Пустой issues без требуемого покрытия не успех.
Обязательные skipped/not_applicable не позволяют подтвердить версию. Политику профиля
и состав правил нужно сверить с ML-командой; Backend не выдаёт её за нормативный эталон.

Необязательный artifacts содержит настоящий Markdown UTF-8, document_id, parser_revision,
полную parser_config и parser_config_hash. Хэш — SHA256 компактного JSON UTF-8 с
sort_keys=true, ensure_ascii=false, separators=(",",":"). На документ/задачу допустим
один Markdown. artifact_id/artifact_locator источника должны относиться к нему.
Если Markdown не производится, передавайте пустой список; выдумывать его не нужно.

## Повторная проверка

check получает выбранный снимок, точную version_id и ранее зафиксированный ruleset,
а также исходный манифест. Проверка не должна молча сменить профиль или набор правил.
Ответ CheckResult содержит coverage и новые issues; новые конфликты могут предлагать
свои варианты для этой версии. Backend сохраняет поздний результат для его входной
версии и не подменяет им проверку другого состояния.

Принять можно только актуальные warning по их UUID. Blocking, нерешённые конфликты,
ошибки файлов и отсутствие завершённой проверки запрещают подтверждение. Подтверждение
человеком фиксирует выбранные данные и не является нормативным заключением.

## Ошибки и ограничения

Настраиваемый предел входного JSON по умолчанию20МиБ, ответа10МиБ, HTTP timeout300с.
Временные ошибки сети/429/5xx повторяет Temporal максимум три раза со стабильным
ключом. Ошибки контракта/4xx не повторяются. Снимки и Markdown не передаются в историю
Temporal: там остаются ID задачи и короткий итог.

Нормализованный result сохраняется в SQL, а исходный ответ анализа сохраняется
в файловом хранилище аудита с JCS SHA-256 и размером. Markdown сохраняется отдельно
как артефакт с SHA-256 исходных UTF-8 байтов; SQL хранит ссылки и метаданные артефактов.
В `raw_result_hash` остаётся SHA-256 компактного JSON исходного ответа до переноса
Markdown; он проверяется по правилам контракта, отдельно от JCS-хэша файла аудита.

Обычное сохранение версии и её восстановление требуют `signature` — подпись
пользователя длиной от 1 до 120 символов. Она записывается в журнал версии, но не
подтверждает личность: API не выполняет аутентификацию.
