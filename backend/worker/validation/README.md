# Этапы проверки

`rules.yaml` задаёт две стадии и режим запуска правил:

- `document_reconciliation` проверяет результаты парсинга до построения графа и
  помогает пользователю разрешить расхождения между документами.
- `graph_validation` запускает автоматические правила по актуальному графу
  после разрешения расхождений документов. На вход передаются проекции именно
  проверяемой версии графа; исходные JSON после правок могут быть устаревшими.
- `run_mode: manual` оставляет правило на стадии графа, но пропускает его в
  обычном запуске. Его можно вызвать отдельно, передав `rule_codes`.

Каждое правило явно перечисляет стадии в `phases`. Для правил, которые должны
работать только на одной стадии, укажите одну фазу. После пользовательского
выбора фронтенд запускает автоматические правила по графу; R-09 и R-11 доступны
отдельными кнопками и не входят в проверку, требуемую для подтверждения версии.

В текущей схеме до графа работают R-01 (сопоставление разных кодов и выбор
списка компетенций дисциплины из учебного плана или рабочей программы),
R-07 (варианты формулировок компетенций) и R-08-semantic
(варианты формулировок индикаторов). После графа выполняются R-01-graph
(проверка итоговых кодов и связей), R-02–R-06, R-03-RPP и R-08-local-reference.
R-09 и R-11 также относятся к графу, но запускаются только по запросу.

Для РПД/РПП с общим списком компетенций R-01 сравнивает его с объединением
списков соответствующих строк плана за все семестры. Если распределение
компетенций из рабочей программы по семестрам неизвестно, эта сторона
не предлагается для переноса в план. Пользователь может сохранить явное
расхождение. Оно останется видимым в итоговой проверке.

Поле `status` управляет доступностью правила независимо от фазы: `ready` и
`ready_with_semantic_fallback` доступны движку, а `draft` пропускаются и не
входят в отчёт. Неизвестный или отсутствующий статус отклоняется при проверке
конфигурации. `run_mode` принимает `automatic` или `manual`; ручное правило не
может быть обязательным для подтверждения версии.

R-07 и R-08 — детерминированные правила группировки и выбора формулировок.
Они используют нормализацию текста, создают варианты для пользователя и не
вызывают LLM; `required_for_confirmation: false` сохраняет прежнюю политику,
при которой эти замечания сами по себе не блокируют подтверждение.

R-09 оценивает покрытие компетенций учебным планом, а R-11 сопоставляет
результаты обучения с содержанием и оцениванием в РПД. Оба правила вызывают
LLM, выполняются только по запросу после построения графа и не заменяют
обязательную автоматическую проверку текущей версии.

Для R-04 проектом утверждено `inputs.hours_per_credit_unit: 36`: валидатор
сопоставляет `hours_total` с `credit_units × 36` в записях дисциплин и
семестровой нагрузки РПД, РПП и учебного плана. Это рабочий параметр проекта;
он сам по себе не устанавливает применимость конкретной редакции ФГОС или ОС
СПбГУ. Поля часов и ЗЕТ в текущем контракте целочисленные, поэтому применяется
точное равенство без округления.

Структурные ограничения самого `SnapshotV2` (уникальность ID, существование
концов связей и источников, корректность provenance) остаются в Pydantic-модели
и проверяются при валидации снимка. Они не дублируются как правила YAML.

При `graph_validation` вызывающая сторона передаёт проекции актуальной версии
графа. Автоматическая проверка и ручные R-09/R-11 сохраняются отдельными
заданиями, чтобы результаты необязательного запуска не подменяли отчёт,
используемый для подтверждения.
