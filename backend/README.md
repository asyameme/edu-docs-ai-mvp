# Бэкенд системы анализа учебных документов

Бэкенд для хранения и последующей обработки документов образовательной программы:
учебного плана, рабочих программ дисциплин, компетенций и связанных данных.

Реализована backend-часть первых двух этапов Roadmap: инфраструктура на Temporal и хранилище программ,
оригинальных файлов и неизменяемых версий. API позволяет создавать программы,
загружать оригиналы, сохранять снимки, читать историю, восстанавливать старое состояние
новой версией и скачивать исходные файлы. Повторные и конкурентные запросы защищены
ключом операции и проверкой ожидаемой версии.

Добавлен контур импорта ZIP: сохранённые задачи, выполнение в Temporal, HTTP-адаптер
ML-парсера, статусы файлов, повтор неудачных файлов и SSE-прогресс в React-интерфейсе.
Рабочий ML-парсер в репозитории не поставляется. Без настроенного `PARSER_URL` задача
заканчивается понятной ошибкой, оригиналы сохраняются. Контракт подключения проверяется
тестовым HTTP-сервером; это не подтверждение реального извлечения из DOCX/XLSX.
Добавлен Backend этапа4: подготовка версии из результатов импорта, сохранение конфликтов
и источников, выбор вариантов, повторная проверка и подтверждение неизменяемой версии.
Реальное междокументное сопоставление и проверки выполняет подключаемый ML-сервис.
Чат и генерация относятся к следующим этапам.
Текущий запуск предназначен для локальной разработки, авторизация и роли отсутствуют.

## Требования

- Docker Desktop с запущенным движком Linux containers и Docker Compose v2.
- PowerShell для команд ниже и полной интеграционной приёмки.
- Свободные порты 8000/8080; для приёмки — 18000/18080.
- Доступ к реестрам контейнеров и пакетам Python при первой сборке.

Python и зависимости устанавливаются внутри контейнера; системный Python не требуется.

## Запуск

Откройте PowerShell в корне скачанного или клонированного репозитория — там, где
находится `compose.yaml`. Этот README расположен в `backend/`.

Для первого запуска создайте локальную конфигурацию, если её ещё нет:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath .env.example -Destination .env
}
notepad .env
```

Замените значения `POSTGRES_PASSWORD` и `TEMPORAL_DB_PASSWORD` на свои разные пароли,
сохраните файл. `.env` исключён из Git; `.env.example` содержит только примеры настройки.
Если база уже создана, сохраняйте её действующие пароли: изменение `.env` само по себе
не меняет пароль существующего пользователя PostgreSQL.

Запустите сервисы и проверьте готовность:

```powershell
docker compose up --build -d
docker compose ps -a
Invoke-RestMethod http://localhost:8000/health/ready
```

При первой сборке запуск может занять несколько минут. Если проверка готовности ещё
не отвечает, дождитесь запуска API и повторите её. Успешный ответ: `status=ready`.

- [Интерфейс программы](http://localhost:8080).
- [Swagger — описание и вызов API](http://localhost:8000/docs).
- [Готовность API](http://localhost:8000/health/ready).

## Проверка через Swagger

1. POST /api/v1/programs с name: получите UUID программы и current_version_id пустой V1.
2. POST .../{program_id}/documents: один DOCX/XLSX/PDF.
3. POST .../{program_id}/versions: expected_version_id=V1, полный snapshot,
   новый заголовок Idempotency-Key. [Пример снимка](examples/snapshot-v1.json); замените UUID
   документа в source_refs и document_ids на полученный при загрузке.
4. GET .../versions и GET .../versions/{version_id}: V1 остаётся неизменной.
5. POST .../versions/{V1}/restore с expected_version_id=V2 и другим ключом создаёт V3
   с пустым состоянием V1. V2 также остаётся доступной.
6. GET .../documents/{document_id}/download возвращает исходные байты.

Повтор того же ключа и запроса возвращает прежнюю версию. Другое тело с тем же ключом
или устаревшая версия дают 409. Загрузка исходника не изменяет снимок:
включите его в следующую версию через document_ids.

## Импорт пакета и подключение парсера

В интерфейсе выберите один ZIP с DOCX/XLSX. Архив — до 50 МиБ, до 50 документов,
общий распакованный объём — до 100 МиБ; каждый файл — до `MAX_UPLOAD_BYTES`.
Нулевые файлы, повреждённые архивы, опасные пути и неподдерживаемые форматы отклоняются
до создания задачи. Одиночные PDF по-прежнему можно сохранять через API оригиналов,
но в пакетный разбор этого этапа PDF не входят.

`POST /api/v1/programs/{program_id}/imports` принимает multipart `file` и обязательный
`Idempotency-Key`, возвращает 202 с ID задачи. Повтор того же содержимого пакета в той
же программе возвращает прежнюю задачу; смена содержимого с прежним ключом даёт 409.
ZIP-порядок и переименование файлов не создают повторную обработку того же содержимого.

- `GET .../imports/{job_id}` — статусы файлов и задача `pending`, `processing`,
  `completed`, `partial` или `failed`.
- `GET .../imports/{job_id}/events` — SSE текущего состояния. После переподключения
  приходит последнее сохранённое состояние, а не полный журнал прошлых событий.
- `POST .../imports/{job_id}/retry` — новая попытка для неудачных файлов. Успешные
  результаты сохраняются; запоздавшие ответы предыдущей попытки не меняют новую.
- `GET .../imports/{job_id}/result` — подготовленный снимок при успешном или частичном
  результате. Его получение не подтверждает программу и не создаёт новую версию.

Прогресс отражает завершённые этапы и документы, а не предполагаемый процент работы
внутри ML-парсера. `completed` означает получение данных без замечаний разбора, но
не прохождение предметных или нормативных проверок. Ошибки части документов и
предупреждения дают `partial`; отсутствие успешных результатов — `failed`.

Базовую часть импорта образуют programs, program_versions, source_documents,
version_documents и processing_jobs. Последняя хранит бизнес-запрос: входную версию,
ключ операции, параметры, namespace/ID процесса и долговечный итоговый отчёт.
Состав загруженного пакета находится в parameters.documents, результаты отдельных
файлов и общий снимок — в report. Они не создают подтверждённую версию программы.

Начальная миграция 0001_initial_schema сразу создаёт эти пять таблиц. Промежуточные
таблицы import_jobs, import_files и import_requests в новой установке не создаются.
Повторный пользовательский
запрос обработки получает новый устойчивый workflow ID; успешно разобранные файлы
сохраняются. Автоматические повторы Activities выполняет Temporal.

Текущий прогресс GET/SSE получает из Workflow Query в Temporal. В SQL нет колонок
runtime-статуса, прогресса, Run ID или состояния диспетчера. Сохранённый итог доступен
после истечения срока хранения истории Temporal; при недоступности живого процесса
API возвращает 503, а не выдуманный процент. Workflow V1 остаётся зарегистрированным
для старых историй; новые задачи используют V2.

Если локально уже применялись прежние миграции, обычный upgrade не заменяет их
новой начальной схемой. Не удаляйте том с данными и не используйте stamp вслепую:
нужны резервная копия, перенос старой схемы и проверка полного совпадения таблиц,
ограничений и индексов с новой начальной схемой. Только после этого допустима смена
служебной отметки Alembic. Для новой пустой базы достаточно обычного запуска Compose.

Формат снимка пока schema_version=1. Markdown-артефакты, отдельные SQL-таблицы
источников и замечаний, новый формат снимка и граф относятся к последующим задачам;
их наличие и готовность не подразумеваются общей таблицей processing_jobs.

Для подключения реального парсера задайте в `.env` его полный HTTP endpoint как
`PARSER_URL` и пересоздайте Worker: `docker compose up -d worker`.
Он получает multipart `file`, дополнительные поля `program_id`, `document_id` и
заголовок `Idempotency-Key`. Ответ — JSON по `backend/contracts/parser_output.py`;
`meta.file_hash` должен совпадать с SHA-256 полученных байтов. Вызов ограничен 90 секундами,
ответ — 10 МиБ. Сетевые ошибки, 429 и 5xx повторяются до трёх раз.

Сущности, ссылки на источники и разные наблюдения не схлопываются автоматически.
Неоднозначная связь сохраняется отдельно с предупреждением, отсутствующее значение
не заменяется нулём. Итог импорта хранится отдельно от неизменяемых версий до этапа
просмотра и подтверждения. Коды и поля, которых нет в контракте ML, не выдумываются.

## Сервисы и хранение

Шесть постоянных сервисов: frontend, api, worker, temporal, postgres, chroma.
Четыре одноразовые службы со статусом Exited (0): temporal-db-init, temporal-schema-init,
temporal-namespace-init, app-migrate. Alembic меняет только базу education.
Temporal использует отдельные базы temporal и temporal_visibility.

Постоянные данные хранятся в томах postgres-data, chroma-data и original-files:
API пишет исходные файлы, Worker читает. Фоновые процессы управляются через Temporal.

Frontend собирается внутри Docker: Node.js проверяет TypeScript и собирает React,
затем Nginx раздаёт готовые HTML, JavaScript и CSS. Node.js на компьютере не требуется.
Запросы `/api/`, `/health/`, `/docs` и `/openapi.json` Nginx передаёт в API.
После изменений интерфейса пересоберите контейнер: `docker compose up --build -d frontend`.
Temporal Server/admin-tools 1.32.1, Python SDK 1.34.0,
namespace education, очередь education-default. История завершённых Workflow — 7 дней;
предметные версии программы хранятся постоянно в PostgreSQL.
Worker выполняет Workflow импорта и отдельную диагностику Temporal.
Chroma запускается, но индексирование программ ещё не реализовано.

## Тесты и диагностика

```powershell
docker compose ps -a
docker compose exec -T api pytest -q -m "not integration"
docker compose exec -T api ruff check app scripts tests migrations
docker compose exec -T api python -m scripts.smoke
docker compose exec -T api python -m scripts.audit_originals
# Полная приёмка:
.\scripts\verify-integration.ps1
```

Полная приёмка использует отдельный случайный Compose-проект, тома и порты 18000/18080.
Основной запуск не останавливается. Проверяются реальный HTTP/PostgreSQL, повторы
Activities, независимые Workflow, отказы зависимостей, перезапуск Worker,
пересоздание контейнеров, оригиналы и повтор миграций. Два таймера по 90 секунд
увеличивают длительность приёмки. Успешное тестовое окружение удаляется вместе с его томами;
при ошибке остаётся для диагностики. -KeepStack сохраняет успешное окружение,
-ResumeProject с напечатанным именем education-acceptance-xxxxxxxx повторяет неудачный запуск.

Обычный pytest без RUN_INTEGRATION=1 пропускает интеграционные тесты: это не полная приёмка.
Readiness проверяет ровно PostgreSQL, Temporal и Chroma с таймаутами; liveness — процесс.
Smoke проверяет настоящий Worker и воспроизведение истории через Replayer.

Проверка HTTP-контракта парсера запускается отдельно, на свободных тестовых портах
18000/18080. Дополнительный сервис из `compose.parser-test.yaml` возвращает искусственные
данные и ошибки; он нужен только тестам и не входит в рабочий запуск.

```powershell
$parserTestProject = 'education-parser-test-' + [guid]::NewGuid().ToString('N').Substring(0,8)
docker compose -p $parserTestProject -f compose.yaml -f compose.test.yaml -f compose.parser-test.yaml up --build -d --wait
docker compose -p $parserTestProject -f compose.yaml -f compose.test.yaml -f compose.parser-test.yaml exec -T -e RUN_INTEGRATION=1 -e PARSER_FIXTURE_TESTS=1 api pytest -q tests/test_import_processing.py
# После проверки удаляется только только что созданный тестовый проект:
docker compose -p $parserTestProject -f compose.yaml -f compose.test.yaml -f compose.parser-test.yaml down -v
```

## Ограничения и обслуживание

Один непустой DOCX/XLSX/PDF до 50 МиБ. MAX_UPLOAD_BYTES настраивается через .env;
Nginx допускает multipart до 64 МиБ — при увеличении лимита измените и его.
parsing_status=not_parsed: расширение разрешено, содержимое пока не разбирается.

Файловая система и БД не образуют общей транзакции. При известной ошибке записи БД
файл удаляется; при потере подтверждения commit оригинал сохраняется. audit_originals
показывает лишние, отсутствующие и временные файлы, без автоматического удаления.

```powershell
docker compose logs --tail 80 api worker temporal app-migrate
docker compose down
docker compose up --build -d
```

`down` сохраняет тома. Не используйте `down -v` для рабочего проекта: эта команда
удаляет тома с данными. Сохранение томов при перезапуске не заменяет резервное копирование.
Предметные поля и контракт обмена требуют согласования с ML на документах команды.

## Четвёртый этап Backend: анализ и подтверждение

Для реального анализа задайте ANALYSIS_URL — базовый адрес ML-сервиса с POST /analyze
и POST /check. Это отдельный обмен, существующий PARSER_URL не меняется. Контракт
и четыре искусственных JSON-примера: examples/review/README.md и contract.schema.json.
До согласования с ML это предложение формата, а не доказательство готовности сервиса.

Миграция0002_stage4_review добавляет source_refs, source_links, validation_issues,
document_artifacts и поддержку Snapshotv2. Итого девять прикладных таблиц, как в SQL-части
черновикаv0.4. Старые снимкиv1 и оригиналы сохраняются. Обратная миграция запрещена,
если уже есть данные этапа4: они не удаляются молча.

Прогресс подготовки/проверки принадлежит Temporal. SQL processing_jobs(type=validate)
хранит цель prepare/check, закреплённую входную версию и долговечный результат.
Источники и замечания фиксируются с версией; выбор и подтверждение создают новые
неизменяемые снимки. В каждой новой версии SourceRef/SourceLink получают новые UUID,
бизнес-ID сущностей сохраняются. Повтор ключа возвращает прежний результат; другой
запрос с тем же ключом программы отклоняется, в том числе между разными типами операций.

API внутри /api/v1/programs/{program_id}:

| Метод и путь | Назначение |
| --- | --- |
| POST /reviews | import_job_id, expected_version_id → 202, подготовка |
| GET /reviews, GET /reviews/{review_id} | Список и прогресс, ссылки на исходную/текущую версию подготовки |
| GET /reviews/{review_id}/events | SSE до конечного состояния |
| GET /versions/{version_id}/review | Конфликты, решения, источники, отчёт проверки и подтверждение |
| POST /reviews/{review_id}/decisions | expected_version_id, conflict_id, variant_id, необязательный check_job_id → 201, новая версия |
| POST /reviews/{review_id}/checks | version_id → 202, проверка |
| GET /reviews/{review_id}/checks/{check_job_id} | Прогресс и долговечный отчёт |
| POST /reviews/{review_id}/confirm | expected_version_id, check_job_id, accepted_warning_ids → 201, подтверждённая версия |
| GET /documents/{document_id}/artifacts/{artifact_id}/download | Неизменяемый Markdown |

Изменяющие маршруты требуют Idempotency-Key. Пагинация review-списка и замечаний:
limit/offset, общий issues_count/conflicts_count. Каждое замечание указывает job_id
и source_version_id: его источники читаются в указанной исторической версии.

Выбор задаётся только предложенным вариантом. Совместимые одинаковые изменения
принимаются, противоречащие/перекрывающиеся поля отклоняются. Замена выбора пересобирает
снимок из исходного анализа, а не оставляет эффекты прежнего варианта. Неизменяемые
validation_issues не переписываются; effective_status вычисляется для выбранной версии.

Подтверждение требует всех решений, завершённой проверки этой версии и её содержимого
по зафиксированному ruleset, отсутствия blocking и явного принятия всех актуальных
warning. Partial импорта из-за предупреждения не равен ошибке файла; ошибки файлов
подготовку запрещают. Пустой список замечаний без покрытия правил не означает успех.
Restore создаёт неподтверждённый снимок; передать confirmation обычным POST /versions
нельзя. Подтверждение не является официальным нормативным заключением.

Если нет ANALYSIS_URL, новый запрос подготовки возвращает503 и не создаёт фиктивного
успеха. Поздний анализ после изменения текущей версии получает outcome=conflict,
сохраняет ответ и не заменяет новую версию. Поздняя проверка остаётся у своей входной
версии. Завершённый отчёт читается и при недоступном Temporal; активный прогресс тогда503.

Original_url в манифесте строится из ANALYSIS_ORIGINAL_BASE_URL (в Compose http://api:8000).
ML может получить оригинал, если ParserOutput не содержит нужного поля. Результат
повторной проверки относится к выбранным данным; исходники остаются неизменными,
поэтому ранее разрешённое различие с одним источником само по себе не должно
бесконечно порождать тот же конфликт заново без новой причины.

Markdown создаётся только из реально переданного artifacts. Он хранится отдельно
в постоянном artifact-files; оригиналы не переносились. Worker пишет производные файлы,
API читает. Конфигурация парсера и SHA256 сохранены. Резервная копия должна включать
SQL, original-files и artifact-files. После сбоя до commit возможен файл без записи:
python -m scripts.audit_artifacts выявляет missing/corrupted/unreferenced, ничего
не удаляя. Уборку выполнять отдельно после сверки незавершённых операций и backup.
Существующая проверка оригиналов остаётся python -m scripts.audit_originals.

Для проверки с искусственным ML на отдельном тестовом проекте:

    docker compose -p education-acceptance-XXXXXXXX -f compose.yaml -f compose.test.yaml -f compose.review-test.yaml up --build -d --wait
    docker compose -p education-acceptance-XXXXXXXX -f compose.yaml -f compose.test.yaml -f compose.review-test.yaml exec -T api pytest tests/test_review_integration.py -q

Вместо XXXXXXXX используйте собственные восемь hex-символов. Порты18000/18080 должны
быть свободны. compose.review-test.yaml запускает только искусственные сервисы:
это проверка Backend-контракта, сохранности и управления задачами, а не настоящий
разбор документов. Продуктовый Frontend и чужие ML/validation-модули этапом не менялись.
