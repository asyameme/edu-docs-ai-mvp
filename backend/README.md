# Бэкенд системы анализа учебных документов

Бэкенд хранит образовательные программы, оригиналы документов и неизменяемые версии
данных. Импорт ZIP выполняется в фоне через Temporal: Worker вызывает парсер, сохраняет
результат и показывает ход обработки через API. Подготовка и подтверждение версии после
импорта — отдельный шаг, для которого нужен сервис анализа.

Встроенный парсер обрабатывает **РПД, РПП, учебный план, характеристику и ЦКМВ
в DOCX**. Матрица компетенций из входного архива не разбирается: она может быть
сформирована из данных документов при генерации.
Авторизации пользователей в API нет; запуск предназначен для локальной разработки.

## Запуск

Нужны Docker Desktop с Linux containers, Docker Compose v2 и свободные порты
8000, 8080, 8233. Команды выполняйте в PowerShell **из корня репозитория**,
где находится `docker-compose.yaml`. Python и Node.js на компьютере не требуются.

Создайте локальные настройки и задайте разные пароли PostgreSQL и Temporal:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath backend/.env.example -Destination .env
}
notepad .env
```

Если база уже создана, используйте её действующие пароли: изменение `.env` не меняет
пароль существующего пользователя PostgreSQL.
Перед запуском новой версии на установке с данными прочитайте раздел
«Данные и обновление» ниже.

```powershell
docker compose up --build -d
docker compose ps -a
Invoke-RestMethod http://localhost:8000/health/ready
```

При первом запуске сборка и подготовка базы могут занять несколько минут.
Успешная проверка готовности возвращает `status=ready`.

- Интерфейс: http://localhost:8080
- Swagger API: http://localhost:8000/docs
- Temporal UI: http://localhost:8233, namespace `education`

## Импорт документов

В интерфейсе загрузите ZIP с папками `РПД`, `РПП`, `Учебный план`,
`Характеристика`, `ЦКМВ` и, при наличии, `Матрица компетенций`.
Первые пять папок содержат DOCX; в папке матрицы лежит XLSX. Имена файлов
внутри папок могут отличаться. XLSX матрицы сохраняется как оригинал, но не создаёт
задачу разбора и не влияет на граф. Другие XLSX встроенный парсер не разбирает.

Ограничения пакета: до 100 обрабатываемых документов,
до 500 МиБ самого архива и распакованных файлов суммарно; отдельный файл —
до `MAX_UPLOAD_BYTES`. Повреждённые архивы и небезопасные пути отклоняются.
PDF можно сохранить как оригинал через API, но в пакетный импорт он не входит.

API импорта: `POST /api/v1/programs/{program_id}/imports` с multipart-полем
`file` и заголовком `Idempotency-Key`. Ответ `202` содержит ID задачи.

| Маршрут относительно `/api/v1/programs/{program_id}` | Что возвращает |
| --- | --- |
| `GET /imports/{job_id}` | Состояние задачи и файлов |
| `GET /imports/{job_id}/events` | Текущий прогресс через SSE |
| `GET /imports/{job_id}/result` | Снимок с узлами, связями и ссылками на источники |
| `POST /imports/{job_id}/retry` | Новую попытку для неудачных файлов |

`partial` означает, что результат есть, но парсер сообщил о замечаниях или часть
файлов не обработалась. `completed` означает завершённый разбор без таких замечаний,
а не прохождение предметной проверки. Результат импорта сам по себе не становится
подтверждённой версией программы.

### Парсер и анализ

При пустом `PARSER_URL` Worker вызывает встроенный парсер для пяти типов DOCX,
указанных выше. После изменения его кода пересоберите Worker:

```powershell
docker compose up --build -d worker
```

Если используется внешний HTTP-парсер, задайте полный адрес endpoint в
`PARSER_URL` и пересоздайте Worker. Он передаёт файл, ID программы и документа
и ожидает JSON по [контракту документа V2](contracts/document_v2/models.py).
Это необязательный режим; отдельный HTTP-сервис для встроенного парсера не нужен.

`ANALYSIS_URL` относится к **другому** сервису: междокументному анализу,
проверкам и подтверждению версии. Без него подготовка review не запускается.
Формат обмена и искусственные примеры находятся в
[документации review](examples/review/README.md).

## Генерация ZIP

`POST /api/v1/programs/{program_id}/generation` принимает заголовок
`Idempotency-Key` и один из вариантов JSON: `{"import_job_id":"UUID завершённого импорта"}`
для сборки без правок либо `{"version_id":"UUID подтверждённой версии"}` для
сборки после выбранных правок. Импорт может иметь статус `partial`, если все
DOCX разобраны и замечания парсера не блокируют сборку.
Запрос создаёт фоновую задачу Temporal и возвращает её ID. Состояние доступно по
`GET /api/v1/programs/{program_id}/generation/{job_id}`; после `completed` ZIP
скачивается по `GET /api/v1/programs/{program_id}/generation/{job_id}/download`.
Повтор с тем же ключом и той же версией возвращает прежнюю задачу.

Worker берёт исходные DOCX из PostgreSQL. При генерации из импорта он сохраняет
их без правок и строит матрицу компетенций XLSX из результата разбора. При
генерации из подтверждённой версии он переносит выбранные точечные изменения
и строит матрицу из этой версии. Задача фиксирует результат импорта при запуске:
повторная обработка архива не меняет уже заказанный ZIP. ZIP
сохраняется в PostgreSQL и остаётся доступным после перезапуска Worker. Пока
генератор меняет только значения полей, для которых есть точная ссылка на
исходный текст; структурные изменения узлов или связей завершаются явной
ошибкой. Имена папок входного архива преобразуются в префиксы имён файлов ZIP.
Для сборки из результата импорта сервис анализа не требуется. Он нужен для
сценария сверки, выбора правок и подтверждения версии.

## Данные и обновление

PostgreSQL хранит оригиналы, версии, редакции графа, журнал правок и готовые ZIP.
Версия ссылается на неизменяемый граф; полный `SnapshotV2` собирается при чтении.
JSON парсера хранится в артефактах, параметры задач содержат ссылки на выбранные данные.
Temporal ведёт выполнение и прогресс. Markdown и исходные ответы анализа для аудита
хранятся в томе `artifact-files`. Chroma запускается,
но индексирование программ пока не реализовано.

**Перед обновлением установки с данными** сохраните резервную копию PostgreSQL
и `artifact-files`. Если установка использует старую схему или том
`original-files`, сначала проверьте путь миграции: простой `upgrade` не всегда
переводит прежнюю схему на новую начальную. Не удаляйте тома и не меняйте отметку
Alembic без проверки данных.

Для обновления установки на текущей схеме из корня репозитория:

```powershell
docker compose build api
docker compose stop frontend api worker
docker compose run --rm app-migrate
docker compose up -d --wait
```

Если миграция завершилась с ошибкой, сначала устраните её и не запускайте новую
версию API/Worker. `docker compose down` сохраняет тома, а `down -v` удаляет их
вместе с данными.

## Проверка и диагностика

Модульные тесты и Ruff запускаются в отдельном тестовом образе:

```powershell
docker build --target test -t education-backend-tests:local ./backend
docker run --rm --network none -e POSTGRES_PASSWORD=test-only education-backend-tests:local pytest -q -m "not integration"
docker run --rm --network none education-backend-tests:local ruff check app scripts tests migrations
```

Проверка работающего стека и сохранённых оригиналов:

```powershell
docker compose exec -T api python -m scripts.smoke
docker compose exec -T api python -m scripts.audit_originals
docker compose logs --tail 80 api worker temporal app-migrate
```

Модульные тесты не проверяют совместную работу PostgreSQL, Temporal и парсера.
Интеграционные проверки запускайте в отдельном Compose-проекте с собственными томами.
