# Бэкенд системы анализа учебных документов

Бэкенд хранит образовательные программы, оригиналы документов и неизменяемые версии
данных. Импорт ZIP выполняется в фоне через Temporal: Worker вызывает парсер, сохраняет
результат и показывает ход обработки через API. Подготовка и подтверждение версии после
импорта — отдельный шаг, для которого нужен сервис анализа.

Встроенный парсер обрабатывает **РПД, РПП, учебный план, характеристику и ЦКМВ
в DOCX**. Матрица компетенций из входного архива не разбирается: она может быть
сформирована из данных документов при генерации.
Авторизации пользователей в API нет; запуск предназначен для локальной разработки.
API принимает имя подписи при сохранении и восстановлении версий, выборе решений и
подтверждении. Интерфейс запрашивает подпись при открытии программы, хранит её
только до закрытия или перезагрузки страницы и позволяет сменить имя. Подпись не
является проверкой личности пользователя.

## Запуск

Нужны Docker Desktop с Linux containers, Docker Compose v2 и свободные порты
8000, 8080, 8233. Команды выполняйте в PowerShell **из корня репозитория**,
где находится `docker-compose.yaml`. Python и Node.js на компьютере не требуются.

Создайте локальные настройки и задайте разные пароли PostgreSQL и Temporal:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath backend/.env.example -Destination .env
}
notepad .env
```

Если база уже создана, используйте её действующие пароли: изменение `.env` не меняет
пароль существующего пользователя PostgreSQL.
Перед запуском новой версии на установке с данными прочитайте раздел
«Данные и обновление» ниже.

```powershell
docker compose up --build -d
docker compose ps -a
Invoke-RestMethod http://localhost:8000/health/ready
```

При первом запуске сборка и подготовка базы могут занять несколько минут.
Успешная проверка готовности возвращает `status=ready`.

- Интерфейс: http://localhost:8080
- Swagger API: http://localhost:8000/docs
- Temporal UI: http://localhost:8233, namespace `education`

## Импорт документов

В интерфейсе загрузите ZIP с папками `РПД`, `РПП`, `Учебный план`,
`Характеристика`, `ЦКМВ` и, при наличии, `Матрица компетенций`.
Первые пять папок содержат DOCX; в папке матрицы лежит XLSX. Имена файлов
внутри папок могут отличаться. XLSX матрицы сохраняется как оригинал, но не создаёт
задачу разбора и не влияет на граф. Другие XLSX встроенный парсер не разбирает.

Ограничения пакета: до 100 обрабатываемых документов,
до 500 МиБ самого архива и распакованных файлов суммарно; отдельный файл —
до `MAX_UPLOAD_BYTES`. Повреждённые архивы и небезопасные пути отклоняются.
PDF можно сохранить как оригинал через API, но в пакетный импорт он не входит.
При загрузке ZIP одновременно распаковываются до четырёх файлов. Worker разбирает
до четырёх файлов одновременно в пределах общей ёмкости очереди активностей;
порядок документов в ответе остаётся таким же, как в архиве.

API импорта: `POST /api/v1/programs/{program_id}/imports` с multipart-полем
`file` и заголовком `Idempotency-Key`. Ответ `202` содержит ID задачи.

| Маршрут относительно `/api/v1/programs/{program_id}` | Что возвращает |
| --- | --- |
| `GET /imports/{job_id}` | Состояние задачи и файлов |
| `GET /imports/{job_id}/events` | Текущий прогресс через SSE |
| `GET /imports/{job_id}/result` | Отдельные документы: document_id, member_name, sha256 и parsed |
| `POST /imports/{job_id}/retry` | Новую попытку для неудачных файлов |

`partial` означает, что результат есть, но парсер сообщил о замечаниях или часть
файлов не обработалась. `completed` означает завершённый разбор без таких замечаний,
а не прохождение предметной проверки. Результат импорта сам по себе не становится
подтверждённой версией программы.
Новый импорт не строит граф. Подготовка через `POST /reviews` анализирует отдельные
документы; граф строится после всех обязательных выборов через `POST /reviews/{id}/decisions`.
Затем запускается `POST /reviews/{id}/checks`, а выбранная версия подтверждается
через `POST /reviews/{id}/confirm`.

### Парсер и анализ

При пустом `PARSER_URL` Worker вызывает встроенный парсер для пяти типов DOCX,
указанных выше. После изменения его кода пересоберите Worker:

```powershell
docker compose up --build -d worker
```

Если используется внешний HTTP-парсер, задайте полный адрес endpoint в
`PARSER_URL` и пересоздайте Worker. Он передаёт файл, ID программы и документа
и ожидает JSON по [контракту документа V2](contracts/document_v2/models.py).
Это необязательный режим; отдельный HTTP-сервис для встроенного парсера не нужен.

`ANALYSIS_URL` относится к **другому** сервису: междокументному анализу,
проверкам и подтверждению версии. Если адрес задан, Backend использует этот внешний
HTTP-контракт; если он пуст, может включиться локальный валидатор, описанный ниже.
Формат внешнего обмена и искусственные примеры находятся в
[документации review](examples/review/README.md).

Если `ANALYSIS_URL` пуст и `LOCAL_VALIDATION_ENABLED=true` (значение по умолчанию),
review запускает существующий валидатор в Temporal Worker. На подготовке Backend
валидирует `PrepareRequestV2`, выполняет `document_reconciliation` и преобразует
находки в `AnalysisV2` без готового графа. Для сопоставимых часов, ЗЕТ и формулировок
предлагаются найденные значения документов с операциями `set_document_value`.
Каждый вариант проверяется на применимость; неоднозначные источники остаются
замечаниями без выдуманного выбора. После всех обязательных решений Backend
строит граф, а check выполняет `graph_validation` по его актуальной проекции.

Локальный профиль автоматически запускает только правила со статусами `ready` и
`ready_with_semantic_fallback`. Правила `draft` остаются в конфигурации, но не
влияют на обычную проверку и её результат, пока не будут утверждены. Их обработчики
можно проверять отдельно тестами, не включая черновики в профиль пользователя.
Неопределённые результаты
смысловых правил сохраняются как `needs_review`, а обязательные неполные проверки
не позволяют подтвердить версию. Worker включает отдельный набор зависимостей
семантического LLM-оценщика. Для вызова модели задайте `VALIDATION_LLM_MODEL` и
`VALIDATION_LLM_API_KEY`; `VALIDATION_LLM_API_BASE` необязателен. Если модель не
настроена или не отвечает, смысловое правило сохраняется как `needs_review`.
В сыром результате для аудита сохраняются `checks` и `evidence`. Публичный ответ
использует контракт main без этих дополнительных полей: ручная проверка обозначается
как `failed` в coverage и `needs_review` у предупреждения с объяснением.
Задание сохраняет использованный профиль правил и исполнителя.

## API чата

Чат закрепляет сессию за одной сохранённой версией программы. API: создать
`POST /api/v1/programs/{program_id}/chat/sessions`, список/восстановление
`GET /api/v1/programs/{program_id}/chat/sessions`, получить сессию и её историю
`GET .../chat/sessions/{session_id}`, отправка
`POST .../chat/sessions/{session_id}/messages`
с `Idempotency-Key`, события `GET .../chat/runs/{run_id}/events` через SSE.
История беседы и безопасный структурированный ответ сохраняются в PostgreSQL;
Temporal выполняет шаги агента и повторно доставляет незапущенные ходы.
Лимиты запросов модели, вызовов инструментов и токенов применяются к одному
пользовательскому ходу, а история и идентификатор диалога сохраняются между ходами.
Инструменты чтения агента только читают данные выбранной версии. По явной
просьбе пользователя агент может запустить проверку этой закреплённой версии
через существующий review API и прочитать её состояние инструментами
`request_program_check` и `read_program_check`. Проверка создаёт обычную
асинхронную check job и не меняет граф. Результаты ограничены по числу правил и
замечаний; статусы `pending`, `partial` и `failed` не выдаются за успешную
проверку. Предложение правки не применяется автоматически. Чтение фрагмента
возвращает исходный текст документа, а не текущее значение графа. Для
сохранённого Markdown-артефакта
используется номер строки; для DOCX локального разбора — координаты парсера
paragraph_index или ячейки таблицы из source_ref.locator. Неподдерживаемый
формат, отсутствующие координаты и неверное место дают явную ошибку инструмента.
Размер фрагмента ограничен.

Завершённый change_proposal остаётся предложением. Явное принятие выполняется
через POST /api/v1/programs/{program_id}/chat/sessions/{session_id}/runs/{turn_id}/accept
с expected_version_id, подписью и Idempotency-Key. Backend проверяет, что граф
не изменился, предложение завершено и не содержит нерешённых вопросов, после
чего применяет его к неизменяемым версиям. Каждый шаг получает отдельную версию
и задачу проверки. Ответ содержит итоговую version и check_job_id; проверка
выполняется асинхронно и читается через
GET /api/v1/programs/{program_id}/reviews/{review_id}/checks/{check_job_id}.
Повтор с тем же ключом возвращает исходный результат; изменение запроса с тем же
ключом или устаревшая версия отклоняются. Предложение с нерешёнными вопросами
нужно уточнить в чате до принятия.

Чтобы включить чат, задайте `CHAT_MODEL`, `CHAT_BASE_URL` и `CHAT_API_KEY` в `.env`.
Задайте также `CHAT_ENABLED=true`, когда ключ настроен. Compose передаёт секрет только
Worker, а API получает признак доступности чата без самого ключа.
Этот признак `CHAT_CREDENTIALS_CONFIGURED` Compose вычисляет из наличия ключа;
пустое значение означает `false`. В другом окружении его нужно передавать API
как метаданные конфигурации. Он не подтверждает, что процесс Worker запущен:
при временной остановке Worker сохранённые ходы ожидают повторной доставки.
При явно включённом чате неполные `CHAT_MODEL`/`CHAT_BASE_URL`/`CHAT_API_KEY`
прерывают запуск общего Worker с понятной ошибкой настройки. При отсутствии ключа
в конфигурации Worker (для Compose — в `.env`) API не принимает новые ходы.
Без аутентификации у локального endpoint используйте явный
непустой placeholder-ключ. При `CHAT_ENABLED=false` агент отключён даже при наличии
старых значений модели и ключа.
`CHAT_MODEL_TIMEOUT_SECONDS` ограничивает ожидание провайдера (по умолчанию 45 секунд);
Temporal повторяет запрос к модели не более трёх раз; после исчерпания попыток ход
сохраняется как `failed`, а SSE возвращает безопасную ошибку. Время одного запуска
Workflow ограничено 15 минутами. История беседы ограничена
512 КиБ, на один запуск заданы пределы 8 запросов к модели, 12 вызовов инструментов,
32 000 входных и 4 000 выходных токенов.
Провайдер должен поддерживать OpenAI-compatible chat completions и structured output.
Для Alibaba Model Studio укажите совместимый endpoint и модель с function calling;
адрес зависит от региона и Workspace ID.
Если параметры модели отсутствуют, API возвращает 503 для отправки сообщений.
SSE передаёт статусы и готовый результат, без частичных токенов.
Сквозные тесты агента используют отдельный OpenAI-compatible ответчик и запускаются
только при `CHAT_AGENT_FIXTURE_TESTS=1`; одного `REVIEW_FIXTURE_TESTS` недостаточно.
Успешный прогон с ответчиком подтверждает связку backend/Temporal, но не заменяет
проверку с настроенным реальным провайдером.

Публичная история содержит `turns`: `id`, `run_id`, `user_text`, `status`, `result`,
`created_at`, `completed_at`. Статус сохранённого хода — `pending`, `completed` или
`failed`; `result` и `completed_at` могут быть `null`. Внутренняя Conversation
в HTTP-ответ не попадает. Результат различается по `kind`: `answer`, `clarification`
или существующий в контракте агента `change_proposal` (только предложение).

SSE использует обычное оформление строками `id:`, `event:`, `data:` с пустой строкой
между событиями. OpenAPI описывает логические поля одного события:

Все чтения статусов Temporal ограничены тремя секундами на один вызов целиком,
включая повторы SDK. При тайм-ауте активных импорта, сверки или генерации API
возвращает 503, не записывая ложный отказ задания в базу. Доставка сохранённых
заданий ограничена пятью секундами на вызов; при сбое она повторяет тот же
workflow ID с запретом дубликатов. Это ограничение ожидания доставки, а не времени
выполнения самого задания.

| event | JSON в data |
|---|---|
| `status` | `run_id`, `status`: `pending` или `processing` |
| `completed` | непосредственно типизированный результат агента с `kind` |
| `failed` | `run_id`, безопасное пользовательское `message` |
| `unavailable` | `run_id`, безопасное `message`: статус временно недоступен; ход может продолжать выполняться |

При `unavailable` клиент закрывает поток и предлагает позже обновить страницу.
Временный сбой чтения Temporal не переводит ход в `failed`. Вызов статуса ограничен
тремя секундами целиком, включая повторы SDK; для ещё не запущенного workflow допускаются
15 последовательных ответов `NOT_FOUND` с секундными паузами.

Неизвестный ход и ход другой программы возвращают JSON 404 до начала SSE;
неверные UUID/тело/заголовок — 422. Повтор ключа с другим сообщением и занятая
сессия — 409, выключенная модель — 503. Все типы графовых сущностей доступны
для фильтрации в инструментах чтения.

Каждый ответ инструмента проверяется после полной JSON-сериализации: максимум
64 КиБ, включая коды связей/правил и другие метаданные. Превышение даёт ограниченный
`ModelRetry`, чтобы агент уточнил запрос; машинные коды при этом не обрезаются.
Поиск возвращает `summary` вокруг совпадения и признак `truncated`. При сокращении
атрибутов `read_entity(query=...)` возвращает ограниченный `matched_context`,
включая совпадения в конце текста или во вложенных/поздних полях.

## Генерация ZIP

`POST /api/v1/programs/{program_id}/generation` принимает заголовок
`Idempotency-Key` и JSON `{"version_id":"UUID проверенной подтверждённой версии"}`.
Новый запрос по одному import_job_id отклоняется: сначала нужны подготовка,
проверка и подтверждение. Импорт может иметь статус `partial`, если все
DOCX разобраны и замечания парсера не блокируют дальнейшую подготовку.
Запрос создаёт фоновую задачу Temporal и возвращает её ID. Состояние доступно по
`GET /api/v1/programs/{program_id}/generation/{job_id}`; после `completed` ZIP
скачивается по `GET /api/v1/programs/{program_id}/generation/{job_id}/download`.
Повтор с тем же ключом и той же версией возвращает прежнюю задачу.

Worker берёт исходные DOCX из PostgreSQL, переносит выбранные точечные изменения
из подтверждённой версии и строит матрицу из этой версии.
Задача фиксирует исходные документы и проверенную версию при запуске:
повторная обработка архива не меняет уже заказанный ZIP. ZIP
сохраняется в PostgreSQL и остаётся доступным после перезапуска Worker.

Генератор заменяет значения с точной ссылкой на исходный текст. Решения R-01
он переносит в отдельные ячейки списка компетенций учебного плана и удаляет
однозначно определённые строки рабочих программ. Добавление компетенции в
рабочую программу требует вручную описать результаты обучения и индикаторы.
Прочие структурные изменения графа пока не поддерживаются.

Если в одной ячейке РПД несколько кодов индикаторов имеют общее описание,
на сверке можно сохранить исходный общий текст или записать формулировки под
каждым кодом. В последнем случае генератор берёт значения из выбранной версии.
При переносе формулировок лишние пробелы и границы абзацев внутри одной
ячейки не мешают найти исходный текст. Повторяющиеся фрагменты требуют
однозначной привязки.

`applied` содержит фактически выполненные замены и удаления, а `notes` —
правки, которые нужно закончить вручную. При наличии таких правок ZIP содержит
файл «Отчёт о сборке.txt». Матрица отражает согласованный граф, поэтому до
ручного исправления она может отличаться от соответствующих DOCX. Имена папок
входного архива преобразуются в префиксы имён файлов ZIP.
Для сценария сверки, выбора правок и подтверждения версии можно использовать
встроенную документную обвязку валидатора или внешний сервис через `ANALYSIS_URL`.

## Данные и обновление

PostgreSQL хранит оригиналы, версии, редакции графа, журнал правок и готовые ZIP.
Версия ссылается на неизменяемый граф; полный `SnapshotV2` собирается при чтении.
JSON парсера хранится в артефактах, параметры задач содержат ссылки на выбранные данные.
Temporal ведёт выполнение и прогресс. Markdown и исходные ответы анализа для аудита
хранятся в томе `artifact-files`. Векторная БД и отдельный поисковый индекс в стеке
не используются.

**Перед обновлением установки с данными** сохраните резервную копию PostgreSQL
и `artifact-files`. Если установка использует старую схему или том
`original-files`, сначала проверьте путь миграции: простой `upgrade` не всегда
переводит прежнюю схему на новую начальную. Не удаляйте тома и не меняйте отметку
Alembic без проверки данных.

Для обновления установки на текущей схеме из корня репозитория:

```powershell
docker compose build api
docker compose stop frontend api worker
docker compose run --rm app-migrate
docker compose up -d --wait
```

Если миграция завершилась с ошибкой, сначала устраните её и не запускайте новую
версию API/Worker. `docker compose down` сохраняет тома, а `down -v` удаляет их
вместе с данными.

## Подпись программы

Миграция `0009_program_signature` добавляет nullable-поле `programs.signature`.
Для существующих программ оно остаётся `null`: имя нельзя достоверно восстановить
из последнего действия другого пользователя. Перед запуском обновлённого API
примените `alembic upgrade head` (штатный Compose выполняет это в `app-migrate`).

`PUT /api/v1/programs/{program_id}/signature` принимает `{ "value": "Анна" }`
и возвращает `ProgramRead`. Пробелы по краям удаляются до проверки длины:
допустимо от 1 до 120 символов Unicode. Некорректное значение даёт 422,
несуществующая программа — 404. GET программы и списка программ возвращает
`signature: string | null`.

Подпись — общее имя программы без пароля, ролей и согласований.
Её можно перезаписать; при одновременных сохранениях действует последнее.
Смена подписи не создаёт версию и не меняет подписи прежних действий в журнале.
Решения, подтверждение и принятие предложения агента по-прежнему получают имя
в теле запроса. Открытая в другом браузере страница получает новое имя при
следующей загрузке программы, включая возврат фокуса на вкладку.
Обновляется и имя на экране, и подпись последующих действий; постоянного push-канала
для синхронизации подписи нет.

Фронтенд восстанавливает имя с сервера при открытии программы. До успешного PUT
используется прежняя подпись; ошибка оставляет редактор открытым. Повторная отправка
блокируется на время запроса, ответ другой программы не меняет текущую подпись.

Проверка: `RUN_INTEGRATION=1 pytest tests/test_signatures.py` с отдельной PostgreSQL.
При ручной приёмке сохраните имя, обновите страницу, откройте программу с отдельным
хранилищем браузера, затем проверьте смену имени и ошибку PUT: прежнее имя должно
сохраниться, редактор — остаться открытым. Для старой программы без имени редактор
открывается, пока подпись не сохранена впервые.


### Контекст беседы с агентом

`CHAT_CONTEXT_TOKENS=200000` задаёт общий ориентир окна запроса (допустимо
32000–200000). Ограничение количества сообщений в сессии снято; старый
`CHAT_MAX_TURNS` больше не используется. Полная видимая переписка остаётся в БД.
Перед запросом в модель выбираются последние целые обмены, которые помещаются
в бюджет. История читается страницами по 100 обменов, а не обрезается до 10.

Подсчёт выполняется локально через tiktoken/cl100k_base и является оценкой для
OpenAI-compatible моделей с другим токенизатором. 20000 токенов внутри общего
окна зарезервированы под инструкции, схемы инструментов и ответ. Текущий вопрос
тоже учитывается. Перед каждым шагом агента контекст повторно ограничивается;
если текущий обмен с результатами инструментов не помещается, возвращается
сообщение о лимите вместо отправки заведомо слишком большого запроса.

В историю последующих ходов входят видимые вопросы, ответы, уточнения и планы
правок; служебные ответы инструментов и рассуждения заново не пересылаются.
Для передачи через Temporal дополнительно действует предел сериализованной
истории 1200000 байт. Счётчик использования сбрасывается для каждого хода;
лимит одного агентного цикла не заменяет размер окна одного запроса.

Модель на сервере должна поддерживать выбранный размер окна: настройка
приложения не расширяет окно модели. Prefix caching, если включён на сервере,
может ускорять обработку одинакового начала запроса, но не заменяет хранение
переписки и не гарантирует постоянное наличие истории на сервере.

Для моделей Qwen задаётся профиль без системных сообщений в середине беседы:
начальные системные инструкции объединяются, а служебные указания повторной
попытки передаются штатным механизмом библиотеки для таких серверов. Это
предотвращает отказ `System message must be at the beginning` при продолжении.
